# Detection coverage and honest limits

SAOS runs deterministic finding rules on **seven tables**: `cmdb_ci`, `cmdb_rel_ci`, `incident`, `task_sla`, `sn_hr_core_case`, `sn_customerservice_case` and `sn_si_incident`. The allow-listed connector can copy metadata from other ServiceNow modules, including `sys_scope` and `sys_app` when readable, but copying a table is not the same as analysing it. Every table not verified during sync is excluded and reported as a coverage gap. It supports both ServiceNow domain-separated records and explicitly configured single-global-domain instances. Domain separation is not the same thing as ServiceNow application scope. **Scoped application code/configuration is inventoried at most, not audited yet.**

| Rule                       | Evidence required                                                                                                                          | What it claims                                           | Next step                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Blank ownership            | `assigned_to`, `owned_by`, `managed_by`, `support_group` are all present and blank                                                         | No owner in those inspected fields                       | Human checks source and selects owner                                             |
| Old discovery date         | Parseable `last_discovered` older than 90 days                                                                                             | Source date exceeds the review threshold                 | Verify CI is still in scope; re-discover                                          |
| Repeated relationship      | Same parent, child, type and domain appear in two records; endpoints visible in same domain                                                | Two relationship rows repeat the same directed edge      | Preview, human approval, live-record recheck, scoped delete and captured rollback |
| Strong identity collision  | Same class and non-empty serial number, asset tag or FQDN appear on multiple CIs in one domain                                             | Possible duplicate identity requiring source-rule review | Human verifies identification rules before merge or retirement                    |
| Priority 1 unassigned work | An `incident`, HR case, customer case or security incident is explicitly active, priority `1`, and has a visible blank `assigned_to` field | A high-priority work item has no assignee in the source  | Check assignment policy and source record; no automatic assignment                |
| Source-reported SLA breach | `task_sla.has_breached` is explicitly `true`                                                                                               | ServiceNow reports a breached SLA; cause is not inferred | Review linked task and SLA definition                                             |

Same CI names alone are not considered duplicate identities. Missing endpoints in an extract are not called broken relationships, because permissions or partial visibility could explain the gap. The UI's rule-strength percentage measures only evidence completeness; it is not a probability that a remediation is safe. Business criticality and service impact remain explicitly unknown until those source fields and graph data are loaded.

Other analysis domains from the SAOS brief—CSDM, security/access, GRC, licensing, flows/business rules, scoped-app metadata, PPM, portal, AI readiness and benchmark—remain unimplemented. Even ITSM, HRSD, CSM and SecOps have only the narrow rules above, not full module coverage. Full-instance extraction inventories allow-listed module tables, but each domain still needs its own deterministic rules and labelled validation set. They must not be presented as clean until those checks are live and verified.

Current pipeline: read-only ServiceNow Table API → verified core CMDB snapshot with excluded optional tables disclosed → narrow deterministic checks on seven source tables → versioned plan → preview → human decision → scoped ServiceNow write only for the approved duplicate-relationship delete → local audit and rollback option. The optional Ollama call only rewrites a finding in simpler language. It does not invent a finding, a risk score or a fix.
